# room-feed

One Douyin live room's chat, gifts and likes, read from the room page in Chrome and sent to local clients (the site's overlays, the chat bot) over WebSocket. The streamer's guide is the site's `/room-feed-windows`; the endpoints are in the [repo README](../README.md#room-feed-live-room-events), and what they send and answer is typed in [`room-feed-protocol/`](../room-feed-protocol).

```sh
pnpm room-feed login             # from the repo root: log in to Douyin in a Chrome window
pnpm room-feed --room <房间号>    # serve that room on port 8757
```

Options: `--port <n>`, `--chrome <path to Chrome>` when it isn't found, `--headed` to see the room's Chrome window. The login is saved in `data/cookie.json` (not in git) and lasts about two months.

How it works: Chrome opens `live.douyin.com/<房间号>` with the saved login, so Douyin's own page does the signing and risk checks. `room-page.ts` watches the page's WebSocket frames over CDP; those that decode as Douyin push frames (`douyin/proto.ts`) are turned into events (`douyin/normalize.ts`) and sent to every client that asked for their type. Chat is sent by typing into the page's chat box; when that fails (no box, a popup over it, the box not emptied by Enter) a screenshot of the page goes to `data/screenshots/` and its path ends the error the client gets. Likes and the 粉丝团灯牌 work the page the same way, as a viewer would: a like holds the like key (z) on the player until Douyin's 「x<N>」 counter by the heart adds up to the number asked for (`like-tally.ts`), and the lamp goes in three steps, each skipped when it's done already: it follows the streamer (the header's 「关注」, shown only while not followed), joins the 粉丝团 (the panel's 「加入粉丝团」, 1 diamond, shown only to a viewer not in it; joining closes the panel) and sends the 灯牌 (the panel's 「送灯牌」, gone once today's is sent, when the line greys out to 「今日第N位送灯牌」). Each click comes 1–2 s (at random) after its button shows, as a person's would. Each step opens the header's 粉丝团 panel and closes its 「我知道了」 notices; sending tries a second opening, as a notice that won't close can keep one from the 灯牌. Both take turns with the chats, since they use the same page. `room.ts` reopens the page when its push sockets all close, the page closes, or no push frame comes within a minute of opening it, waiting 5 s, 15 s, 30 s, then 60 s between tries in a row. It exits instead when there's nothing to wait for: Douyin says the stream has ended (a `WebcastControlMessage` with status 3, which comes just before it closes the chat socket; reopening then landed on another live room Douyin moved the page on to), the stream has ended, or hasn't started, as the page opens (`webcast/room/web/enter/` says status 4, or the page shows 直播已结束), so start it once the room is live; or a push message carries another room's id than the one the enter answer gave (Douyin's page moved to a room it recommends; the log has the page's address and a screenshot in `data/screenshots/`). Before it exits it sends every client an `__ended` frame (`reason`: `ended` or `wrongRoom`, `detail`: the reason in words), which `RoomFeedClient` reports as status `ended`, and closes their sockets cleanly. Exit code 0 on an ended stream, 1 on another room.

It started as a cut-down copy of [ymstar/dyhub](https://github.com/ymstar/dyhub), whose MIT licence is in [LICENSE](LICENSE): the protobuf schema, the message normaliser and the room-page code come from there.
