# AGENTS.md (chat-bot)

How to run the chat bot for the user, e.g. when they say 「启动机器人，房间 123」 or 「停掉机器人」. What the bot does and every option are in the [README](README.md).

## Start

The user gives a room number (the digits in `live.douyin.com/<id>`). Start three processes, always in this order and one at a time (each its own Bash call with `run_in_background`, never `&` or `nohup`, so they can be stopped later; never two in the same message, whose order isn't fixed): the speech service, then, once it's ready (step 3), the bot, then, once the bot is waiting for room-feed (step 5), room-feed.

1. **Check nothing is running yet**: `lsof -nP -iTCP:8757 -sTCP:LISTEN` (room-feed), `lsof -nP -iTCP:8758 -sTCP:LISTEN` (the speech service) and `pgrep -fl "transcribe.py|src/main.ts .*--bot-name"`. Skip a step whose process is already up; if a bot is already running (a `src/main.ts … --bot-name` process), ask before starting a second one (the speech service serves one bot at a time).
2. **The speech service**, from `chat-bot/`: `uv run --directory asr transcribe.py --serve 8758`. The bot never starts it; it only connects. It keeps its models loaded across restarts of the bot, so leave it running when only the bot is restarted. The one time it goes by itself: when room-feed is gone, the bot tells it to quit as the bot exits (below). Skip it with `--no-asr` on the bot.
3. **The speech service is ready**: its output has `[asr] serving on 127.0.0.1:8758`, printed once the models are loaded (about half a minute; up to a few minutes on the first run ever, which downloads about 10 GB of them first; one that was already running from before, step 1, is ready). If it never comes, its output says why; tell the user, and start the bot with `--no-asr` only if they want it without speech.
4. **The bot**, from `chat-bot/`:

   ```sh
   pnpm start --room <房间号> --bot-name 默认关闭 --bot-id 7692586790687114297
   ```

   A room's settings (`--screenshot`, `--auto-reply-threshold`, …) live in its `data/<房间号>/room_config.json`: an option only seeds one the first time, when the file has no such field; after that the file wins (the bot warns `setting from room_config, ignoring option` when an option differs). To change a setting later use the command (`/自动回复阈值 0.6`, which writes the file) or edit the field in `room_config.json` by hand: either takes effect at once, no restart. Fields and defaults are in [docs/room-setup.md](docs/room-setup.md).

   Add `--screenshot` when the stream is a lesson or game where Claude needs to see the video (a board, a question on screen); the user may ask for it. Without it, an admin can still turn screenshots on in the room while it runs: `/截图 1` (and `/截图 0` to turn them off). Every command is listed in [docs/commands.md](docs/commands.md).

   `默认关闭` / `7692586790687114297` is the Douyin account room-feed is logged in as. If the user logged in with another account, get its nickname from them and its uid from the `user.id` of one of its own chat messages (in `logs/chat-bot.log`).

5. **The bot is waiting for room-feed**: its output has `mcp server listening` and `room-feed error` (`无法连接 localhost:8757，请确认 room-feed 已启动`). That's expected: the client keeps trying until room-feed is up. A bot that exits here instead (`EADDRINUSE`, say) says why; tell the user.
6. **room-feed**, from the repo root: `pnpm room-feed --room <房间号>`. It serves only that room, so if one is already running for another room, stop it first (ask if it isn't one you started). Wait until `curl -s localhost:8757/api/rooms/<房间号>` answers.
7. **Check the login** in that answer: `room.login` must not be `null` (and its `expiresAt` must be in the future). Without it the bot can't send chat and gifts don't arrive: stop all three (see Stop), ask the user to run `pnpm room-feed login` from the repo root (it opens a Chrome window to log in to Douyin, then exits), and start again from step 1 once they have.
8. **The room is live**: `room.status` turns from `connecting` to `live` within seconds once the room is streaming. room-feed reopens the room page by itself whenever its chat drops, so there's nothing to clean up between bots. It exits by itself (`直播已结束，不再重新打开直播间`) when the room isn't streaming as it opens the page, at the start or on a reopen after the stream ended, and when the page shows another room (the room-number check). When room-feed goes away after the bot was connected to it (it exited, or was stopped), the bot logs `room-feed is gone, stopping` (with room-feed's reason as `detail`, like 直播已结束, when room-feed exited by itself; it sends `room-feed ended` just before), tells the speech service to quit, and exits too: all three are down, and the next show starts from step 1.
9. **Confirm it's working** from the bot's output, and tell the user:
   - `room-feed ready` within seconds of room-feed starting: connected to the room's chat.
   - `transcribing {"url": …}`: room-feed has the stream. If it never comes, the room isn't live.
   - `heard {"text": …}` soon after `room-feed ready`: speech recognition is running. The bot connects to the speech service on port 8758 (`--asr-port`) and, while it's still loading its models, waits for them (up to 3 minutes) before it enters the room. With no service running it enters at once, without speech, logs `could not start the transcriber` (`no speech service on port 8758: start it first, …`) once, and connects by itself within 10 s of the service being started.
   - `gift {…}` lines as viewers send gifts.

10. **Recording the audio**, only when the user asks (「录音」「turn on recording」): once the bot is up, from `chat-bot/`, with `run_in_background`: `scripts/record-stream.sh <房间号>`. It copies the stream's AAC as it is into `data/<房间号>/recordings/stream-<UTC time>.aac` (about 60 MB an hour), asking room-feed for the signed URL (`GET /api/rooms/<房间号>/stream`; the URL in the bot's log has its signature cut off and gets 403). A drop starts a new file, and it stops by itself within 10 s of the bot exiting. Check the file grows with `ffprobe` after a minute.

## While it runs

- In someone else's room, the bot answers anyone who @s it, in public, as the user's account, and, when turned on (`--auto-reply-threshold 0.6` or `/自动回复阈值 0.6`; off by default), joins in when people talk to or about it without an @ (Jev, with `JEV_API_KEY` in `chat-bot/.env`; at most once a minute, or every `--auto-reply-interval` seconds; `/自动回复间隔 0` for a busy room). Gift thanks (`--thanks-threshold`, `/自动谢礼`) are off by default too. Say so when starting it there.
- Read `chat-bot/logs/chat-bot.log` (JSON lines: every chat, prompt, answer, gift and transcript line) to answer questions like 「刚才机器人回了什么」 or 「谁送了礼物」. Every call to a model logs as it starts and ends, with what it was for and how long it took: `claude asking` / `claude answered` / `claude failed` `{task, ms}`, the same for `codex` (and `jev`, at debug). The tasks are `mention`, `gift-thanks`, `auto-message` (Claude), `reply-pick`, `song-id`, `malice`, `puzzle` (Codex), and `about-the-bot`, `malice` (Jev); `lyrics search {why, ms, sure, title, artist, artistShare, queries, top}` is NetEase's lyrics search naming a song before Codex is asked, and `song identified {by}` says which answered (`shazam`, asked first while the streamer sings, `lyrics-search` or `codex`); `lyrics kept {title, artist, lines}` / `no lyrics for {title}` is the named song's lyrics fetched to tell where it ends, and `song changed {by, …}` a song break source starting the next song: `by: "lyrics"` (`from, line, at, misses`), `"shazam"` (`title, at`: the backing track Shazam named changed) or `"backingGaps"` (`at, quietMs, line`: the backing track stopped), the last two from the speech service's add-ons (`backing: …` in its output; `--no-backing-title` / `--no-backing-gaps` on `transcribe.py`) (see `/识歌` in docs/commands.md, and `songBreaks` in docs/room-setup.md); `mcp tool {tool, asker, userId, ms, isError}` is Claude calling one of the bot's tools (any of the tools in the table in [docs/commands.md](docs/commands.md)), and `mcp server listening {port}` the server starting; `claude answered` has `tools: [{tool, ms, isError}]` (what Claude called, and how long each took) and `unprompted` (when it wasn't an @), so the latency of an answer with and without tools can be compared from the log; `tool guidance {name, asker, userId}` is a declarative tool handing Claude its guidance, `fixed reply {name, asker}` one sending its fixed text, `skipped by user filter {name, asker, userId}` one the viewer's `only` / `except` left out, `tool definition {name, folder, adminOnly, listen}` one loaded from `src/mcp/tools/` (at start, and when a `tool.json` changes); `command {name, args, ok, ms}` is a typed `/`, `setting {command, before, after}` a setting changed by a tool, `sure about the bot {who, text, score}` a line auto-reply answered without the picker (Jev over 0.9), and `puzzle answered` / `could not answer about the puzzle` the background solve of `ask_about_puzzle`; whom Codex chose to answer is `picked whom to answer` (`[]`: nobody). `claude skipped` is Claude choosing to say nothing (the usual prompt allows it).
- Song messages: Codex writes the one message that tells the room a song (`song-id.md`), with the title and singer woven in, not a fixed 「这首是…」: when Shazam or the lyrics search named it, Codex is given the song (`song-known` in `wording.md`) and only writes; otherwise it finds the song and writes in the same call. The program's sentence (`song-found`) goes out when Codex fails or leaves the title out (`song message {title, hook, message, named}` in the log), and for Claude's `identify_song`, whose own reply is the message. One in four messages to the room (the program rolls it, `hookChance` 0.25 in `src/app/songs/song-id.ts`) is asked to end with a hook anyone in the room can answer, about the song or its work; the rest ask nothing (`song-hook` / `song-no-hook`).
- The room's chat record is in `chat-bot/data/<房间号>/chat/*.txt`, one line per speech (`[主播](speech)`, `(sing)` when sung, or `(play)` for a recording she played, found by Shazam; `[主播](song) 《…》唱完了，下一首从 HH:MM:SS 开始（why）` when one of her songs ended, written once the next one started, `src/app/songs/song-ends.ts`), chat or gift (`[昵称#uid](gift)`), 100 lines a file; it's kept across runs. Times are in the room's `timeZone` with the offset, and a chat's sender carries what they wear after `|` as room-feed sends it (`V`/`V年` 直播间会员, `灯牌N` fan club level, `财富N` wealth level): `2026-10-21 16:32:46+08:00 [阿拂#103094206072|V|灯牌16|财富34](chat) 那发给我康康？`. Lines without an offset were written before, in the machine's time zone.
- The prompts (`chat-bot/prompts/prompt.md`, `song-id.md`, `solve.md`, `gift-thanks.md`, `auto-message.md`, `reply-pick.md`, `malice.md`, `intro.md`, what the bot says about itself, `limitations.md`, what it can't do and why (for when viewers notice something wrong), and `wording.md`, the sentences the program says around what it fills in: Jev's questions, how a prompt says who asked what, the picker's room-command rules, the song-id notes; unlike the prompts, a room can't override it) are shared by every room, and each room's `chat-bot/data/<房间号>/memory.md` (what the bot remembers about the room, in every prompt; the bot writes it with `update_memory`, and anyone may edit it) holds what's particular to it; a room overrides a prompt with its own file of the same name, `_` for `-` (`song-id.md` by `song_id.md`; `prompt.md` has no room override), see `PROMPT_FILES` in `src/adapters/files/prompt-files.ts`. All are read on every use: edit them to change the bot while it runs, no restart needed. `bot_logs.md` there has everything the bot sent, `<uid>/talk.txt` each viewer's exchanges with it, and `<uid>/note.md` what the bot remembers about them (the streamer's is in every prompt; see "What the bot remembers" in docs/commands.md). `memory updated` in the log is each change the bot made to either.
- Files to fetch on entering a room: list them in its `room_config.json` as `"download": [{ "url": "https://…", "file": "songs.txt", "transformer": "tools/can-sing/songs-transformer.js" }]`. Each time the bot starts there it fetches every one into `chat-bot/data/<房间号>/artifacts/<file>`, replacing the old copy, in the background (`src/adapters/files/room-downloads.ts`). `file` must be a bare file name. `transformer` (optional) is a script in the room's folder: it runs with Node in that folder, gets what was fetched on stdin, and what it prints is kept instead (so a big JSON can become a short list for a prompt). A failed download or transformer is a `download failed` warning in the log and keeps the old file. The list is read only at start, so restart the bot after you change it.
- Something to say when the streamer starts a song: `"on_sing": { "message": "…", "probability": 0.67 }` in the room's `room_config.json`. With that probability, the message goes out as it is once per song: when singing starts after a pause, and again every 3 minutes of nonstop singing (`src/app/songs/on-sing.ts`). It needs speech recognition, but not `/自动识歌`. The file is read again when it changes, so no restart is needed; leave `on_sing` out to turn it off.
- Talking on its own every so often: every `autoMessageIntervalSeconds` (`/自动消息间隔 300`, or the field in `room_config.json`, read hot; `0`, the default, is off; nothing to do with `/自动回复间隔`) Claude reads the room with `prompts/auto-message.md` (`auto_message.md` in a room overrides it) and says one message in the room's persona, or nothing (`src/app/replies/auto-message.ts`). The log has `auto message {text}`, or `auto message: nothing to say`.
- Viewers to always answer: `"focus": ["103094206072"]` in the room's `room_config.json` (user ids in quotes, read again when it changes). Every chat from one of them goes to Claude at once, like an @, without Jev or Codex, auto-reply on or off; Claude may still say nothing. `focus {who, userId, text}` in the log.
- Other names for the bot: `"aliases": [{ "name": "Fairy", "heardAs": ["ferry"] }, { "name": "菲瑞", "heardAs": [] }]` in the room's `room_config.json` (read again when it changes, no restart). When auto-reply is on, a line calling the bot by its account nickname (默认关闭) or an alias is answered at once by Claude, like an @, without Jev or Codex, and without waiting for the 20-second check or the quiet time (`src/app/replies/auto-reply.ts`, `hear` / `hearSpeech`); the check after leaves that line out. A chat must contain the name as written (Latin letters in any case). The streamer's speech may also have a `heardAs` form (how speech recognition writes it, any case), or, for an all-Chinese name, something with the same pinyin (默认关壁 for 默认关闭, with the sounds people mix up merged, `src/core/viewers/sounds-like.ts`); matching is in `src/core/viewers/alias.ts`. Claude may say nothing (`claude skipped`) when the line isn't really for it or only ends the talk (「谢谢」), see `prompt.md`. It's in the room's own file; never put a room's aliases in `src/` or the shared prompts. To see how often it fires and how often that's a false positive: `name called` (`name`, `who`, `text`, `heard`) is each one answered, `claude skipped` (`asker`, `question`) each the bot said nothing to; `name called, streamer unknown` is the streamer calling it before the bot knows who they are. The picker's calls say why they were made, `jq -r 'select(.message=="codex asking" and .task=="reply-pick") | .why' logs/chat-bot.log | sort | uniq -c` (`follow-up`, `trigger` or `judge`).
- How to set a room up (room_config.json, memory.md, its tools, prompt placeholders, what needs a restart) is in [docs/room-setup.md](docs/room-setup.md). In short: a room switches tools on with `"tools": ["can_sing", …]` in its `room_config.json` (read again when it changes). The tools are defined in the repo, in `src/mcp/tools/<folder>/` (the folder is the name with `-` for `_`): `tool.json` has `name`, `description` (what Claude reads to route by), `guidance` or `fixedReply`, `adminOnly`, `only` / `except` (user filters, lists of `{ "badge"?, "fansLevel"?, "payLevel"?, "admin"? }`: a viewer matches a list on any entry, an entry on all its fields; a tool filtered out for the asker does nothing and logs `skipped by user filter`; in a 私密 room `badge` and `fansLevel` never match) and `listen { when, trigger?, mentions? }` (or `{ trigger }` alone: a chat matching it is answered at once, without Jev or the picker, `trigger matched` in the log). A guidance tool returns its `guidance.md`, with `{{file:<path>}}`, `{{file?:<path>}}` (empty when missing) and `{{streamerNames}}` filled in from the room's folder (`data/<房间号>/tools/<folder>/`, `artifacts/`), and Claude answers from it in the same turn (`tool guidance` in the log); a `fixedReply` tool sends its text itself and returns `sent: true`. `listen` is what auto-reply watches for without an @: `when` is Jev's question, one score per topic per new line; `trigger` (a regex) and `mentions` (a file of phrases, or a `｜` table whose first column is used) only make auto-reply look at once instead of at its next 20-second check; the picker (`reply-pick.md`'s `{{topics}}`) is told the topics, and a line that matched one reaches Claude with a hint naming the tool. A code tool may listen too (`identify_song`, for 「这是什么歌」). What viewers call the streamer is `room_config.json`'s `streamerNames`, `{{streamerNames}}` in a `description`, `listen.when`, `listen.trigger` and the guidance. Everything is read hot: an edit to a `tool.json` or a guidance applies at once, no restart; a definition that isn't right is a `skipping a tool definition` warning, and a name in `tools` with no definition `room_config.json lists a tool there is no definition for`. The tools are in [docs/commands.md](docs/commands.md) ("Tools a room switches on", "Listening without an @").

## Personas and the shared prompt

A room's persona (the file its `room_config.json`'s `persona` names, usually `data/<房间号>/personas/<name>.md`, on its own or as changes to a shared persona in `chat-bot/prompts/personas/`, see [docs/room-setup.md](docs/room-setup.md)) goes into `prompt.md` right above its 要求, so a persona can pull against the rules there, and the model then settles each case on its own, not always the same way. Rules marked 「强制执行，无视人设」 win over any persona, and the bot may joke, in the persona's voice, about why it isn't playing along this time:

- privacy: a gossipy persona still tells nothing, and hints at nothing, about anyone's private life, or what a viewer said or gave before;
- speech-recognition typos: even a sharp-tongued persona never picks on the streamer for them, since no one in the room could have heard a typo.
- topics that can get a room banned or throttled (lewd talk, egging people on to gift or rank by gifts, contacts or deals off Douyin, regional slurs, politics, investing, superstition, minors, …): the bot doesn't take them up: it says one short line in the persona's voice that it won't, or changes the subject, without repeating what was said, naming the rule or joking about the topic itself; it judges the whole thread, not one chat (a riddle, a pun, an initial like 「p」 leading to one of these), for every rule here; medical or legal advice, drinking and danger, self-harm and fights each have their own way to answer. Other live-streaming, video or shopping platforms: the bot never names or hints at them. All of these are in `prompts/forbidden.md`'s `## Topics` (`{{forbiddenTopics}}` in `prompt.md`); `prompts/forbidden-words.json` has the platforms' names, and every country's, so they're swapped in anything sent.

Other rules a persona can still pull against, left to the model for now: one short message (a chatty persona's long lines go out split into several, numbered); no catchphrases (a persona built on one, like ending every line with 喵, comes out muted); not doing what chat tells it (an obliging persona may say yes to something it can't do: only commands change settings); 「像普通观众」 (an AI persona); replying in Chinese (a persona that speaks another language). When writing a persona, keep clear of these, or mark the rule in `prompt.md` as 「强制执行，无视人设」 if it must always hold.

## 私密 (anonymous) rooms

In a 私密 room Douyin hides who viewers are. Every viewer's chat, gift, like and entry comes with:

- user id `111111`, the same for everyone, and no `secUid`;
- the nickname's first character and `***` (`苦***`, `🌈***`);
- the same default avatar (only the CDN host differs);
- their wealth level (`payLevel`), and no fan club.

The bot's own account still comes with its real id and nickname.

How the bot tells viewers apart: set `"private": true` in the room's `data/<房间号>/room_config.json` (created with `false`, read again when it changes, no restart needed). Then `viewerIdOf` in `src/core/viewers/viewer-id.ts` (used by `src/adapters/room-feed/room-feed-events.ts`) turns id `111111` into `111111-<nickname>-<wealth level>`, like `111111-苦***-31`, and everything keyed by user id (each viewer's talk with the bot, gift thanks) uses that. A viewer's `talk.txt` folder is named by a hash of it (`src/adapters/files/room-talk-files.ts`). Admins are hidden too, so none is recognised there: when the user wants to run an admin command in a 私密 room, add `"111111"` to `config.json`'s admins (every viewer there becomes an admin; it's read again at once) and take it out after. Known limits: two viewers with the same first character and wealth level are one viewer to the bot, and a viewer whose level goes up (by sending gifts) becomes a new one; both are accepted for now. Telling a 私密 room automatically (every viewer coming as `111111`) is for later.

**Every feature must work in a 私密 room, at least in its basics.** When you add or change a feature:

- Key viewers by the user id the adapter gives (like `<uid>/note.md`, what the bot remembers about a viewer; the memory files and their rules are `@dy-apps/room-memory`'s) (never by `111111`, the raw nickname or the avatar), and don't assume ids are digits.
- Don't rely on a viewer's full nickname, avatar, `secUid` or fan club; with only `苦***`, the feature should still do its job (answer an @, thank a gift, remember their talk with the bot).
- Add a test with 私密 viewers (id `111111`, a `X***` nickname, a wealth level) when the feature handles users.

## Declarative tools

**A declarative tool's specifics (its description, guidance, filters and listen) live in `src/mcp/tools/<folder>/`, with nothing about one room in them; what differs per room (the streamer's names, the song list, notes, the streamer's hours) lives in the room's folder, `data/<房间号>/`, and is read with `{{file:…}}`, `{{file?:…}}` and `{{streamerNames}}`.** The program knows nothing of what a tool says beyond the protocol (`name`, `description`, `guidance`, `fixedReply`, `adminOnly`, `only`, `except`, `listen`), and the docs are in [docs/room-setup.md](docs/room-setup.md) and [docs/commands.md](docs/commands.md). When you add or change one:

- Don't put a tool's specifics in `src/` logic or the shared prompts: no song lists, song or schedule wording, no tool names in logic, and no example of one tool in rules every tool gets (`reply-pick.md`, `prompt.md`). Something a tool needs Claude, Jev or Codex to know goes in its `description` (what Claude reads) or its `listen.when` (what Jev and the picker read).
- Don't make the program read a room's files in their own format. A file a guidance needs goes in through `{{file:…}}`, already in the shape the guidance wants; turning a download into that shape is the room's `transformer`'s job.
- If a tool needs something the protocol can't give it, add a general part to the protocol (like `{{file:…}}`) and document it in docs/room-setup.md, rather than handling that one tool in code.

## Stop

Stop the bot's background task first (a recorder, if one is running, stops with it), then room-feed's, then the speech service's (TaskStop each; leave the speech service running when the bot is only being restarted), and check with the `pgrep` and `lsof` commands above that no `transcribe.py`, `ffmpeg` or room-feed process is left.

After a stream (the bot stopped by you, or gone with room-feed), read its chat into memory, from `chat-bot/`, with the bot's room and account: `pnpm remember --room <房间号> --bot-name 默认关闭 --bot-id 7692586790687114297` (half a minute or so; see "Reading the chat into memory" in docs/commands.md). Tell the user what it changed: the `memory updated` lines with `by: "chat"` in `logs/chat-bot.log`, and any `memory change skipped` (it never rewrites or removes what the streamer or an admin wrote in memory.md, only adds to it; replaced and removed entries are kept in `data/<房间号>/memory/archive.md`, and each run adds a summary of the stream to `memory/streams.md`). Not when the bot was only restarted mid-stream.

## Troubleshooting

- Switching to another room: the speech service keeps the voices it learned, and doesn't know the room changed, so the old room's streamer stays "the streamer" and the new one's talk comes out as `（连线）` (`host: false` in `heard`). Restart the speech service (step 2) when switching rooms, until it resets voices on its own.

- `stream ended, asking for it again` now and then is normal (the stream URL expires or the stream drops): the worker keeps its models loaded and gets the new URL within seconds, or every 10 s while there's no stream. `transcriber stopped, restarting` means the connection to the speech service ended: the bot connects again within 10 s. If the service itself died, its task's output says why; start it again (step 2) and the bot reconnects by itself. If either repeats, `GET localhost:8757/api/rooms/<房间号>/stream` shows whether room-feed still has a stream.
- `the speech service is serving another bot; trying again later`: another bot (another room, or an old one still exiting) is connected to the speech service, which serves one at a time; this bot enters the room without speech and tries every 10 s. `speech recognition is not ready yet, entering the room without it` (after 3 minutes): the service is still loading or stuck; see its output.
- `reply did not show up in the room chat`: Douyin may be throttling the account, or held this message back for a word it filters (others still show up then). In that case add the word to `prompts/forbidden-words.json`: it's swapped for `*`s (or the replacement you give it) in everything the bot sends.
- `could not answer mention … claude …`: run `claude -p` by hand to check Claude Code works.
- `jev is out of credit, auto-reply off`: the TypeSafe account ran dry; the bot told the room (`钱包烧干了，自动回复已关闭`) and set the threshold to 10. Tell the user to top it up, then an admin can turn it back on with `/自动回复阈值 0.6`.
- `no JEV_API_KEY` at start (or `--codex is empty`), or `could not judge` now and then: the bot then doesn't talk unprompted, only when @ed. Check `chat-bot/.env` has `JEV_API_KEY` (a TypeSafe key) and that `curl -s -H "Authorization: Bearer $JEV_API_KEY" https://api.typesafe.ai/v1/models` answers.
- `lyrics search failed`, or `lyrics search` with `why: netease down` / `netease failed`: NetEase's lyrics search is unreachable or has changed (3 failures in a row stop it for 10 minutes); Codex takes over by itself, slower (10–36 s), so nothing needs doing. `--no-lyrics-search` turns it off. `could not start` with `EADDRINUSE` at start: the tools' port is taken (`--mcp-port`); the bot exits, since without its tools Claude can't act on anything said in words.
- `/识歌 … codex failed`: Codex isn't logged in or ran out of quota; `codex login` logs in. `ask_about_puzzle` (`/解题`) uses Codex too.
- Changed the code? Run `pnpm typecheck`, `pnpm test` and `pnpm lint` (from the repo root) before restarting it.
