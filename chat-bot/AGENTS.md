# AGENTS.md (chat-bot)

How to run the chat bot for the user, e.g. when they say 「启动机器人，房间 123」 or 「停掉机器人」. What the bot does and every option are in the [README](README.md).

## Start

The user gives a room number (the digits in `live.douyin.com/<id>`). Start three processes, in this order, each with the Bash tool's `run_in_background`, never `&` or `nohup`, so they can be stopped later.

1. **Check nothing is running yet**: `lsof -nP -iTCP:8757 -sTCP:LISTEN` (room-feed), `lsof -nP -iTCP:8758 -sTCP:LISTEN` (the speech service) and `pgrep -fl "transcribe.py|src/main.ts .*--bot-name"`. Skip a step whose process is already up; if a bot is already running (a `src/main.ts … --bot-name` process), ask before starting a second one (the speech service serves one bot at a time).
2. **The speech service**, from `chat-bot/`: `uv run --directory asr transcribe.py --serve 8758`. The bot never starts it; it only connects. It listens at once and loads the models in about half a minute (the first run ever downloads about 10 GB of them first), so go on with room-feed meanwhile. It keeps them loaded across restarts of the bot, so leave it running when only the bot is restarted. The one time it goes by itself: when room-feed is gone, the bot tells it to quit as the bot exits (below). Skip it with `--no-asr` on the bot.
3. **room-feed**, from the repo root: `pnpm room-feed --room <房间号>`. It serves only that room, so if one is already running for another room, stop it first (ask if it isn't one you started). Wait until `curl -s localhost:8757/api/rooms/<房间号>` answers.
4. **Check the login** in that answer: `room.login` must not be `null` (and its `expiresAt` must be in the future). Without it the bot can't send chat and gifts don't arrive: ask the user to run `pnpm room-feed login` from the repo root (it opens a Chrome window to log in to Douyin, then exits), then restart room-feed, and stop here until they have.
5. **The room is live**: `room.status` turns from `connecting` to `live` within seconds once the room is streaming. room-feed reopens the room page by itself whenever its chat drops, so there's nothing to clean up between bots. It exits by itself (`直播已结束，不再重新打开直播间`) when the room isn't streaming as it opens the page, at the start or on a reopen after the stream ended, and when the page shows another room (the room-number check): start it again once the streamer is live. When room-feed goes away after the bot was connected to it (it exited, or was stopped), the bot logs `room-feed is gone, stopping`, tells the speech service to quit, and exits too: all three are down, and the next show starts from step 1. A room-feed that isn't up yet when the bot starts is waited for, as before.
6. **The bot**, from `chat-bot/`:

   ```sh
   pnpm start --room <房间号> --bot-name 默认关闭 --bot-id 7692586790687114297
   ```

   A room's settings (`--cost`, `--screenshot`, `--auto-reply-threshold`, …) live in its `data/<房间号>/room_config.json`: an option only seeds one the first time, when the file has no such field; after that the file wins (the bot warns `setting from room_config, ignoring option` when an option differs). To change a setting later use the command (`/自动回复阈值 0.6`, which writes the file) or edit the field in `room_config.json` by hand: either takes effect at once, no restart. Fields and defaults are in [docs/room-setup.md](docs/room-setup.md).

   Add `--screenshot` when the stream is a lesson or game where Claude needs to see the video (a board, a question on screen); the user may ask for it. Without it, an admin can still turn screenshots on in the room while it runs: `/截图 1` (and `/截图 0` to turn them off). Every command is listed in [commands.md](commands.md).

   `默认关闭` / `7692586790687114297` is the Douyin account room-feed is logged in as. If the user logged in with another account, get its nickname from them and its uid from the `user.id` of one of its own chat messages (in `logs/chat-bot.log`).

7. **Confirm it's working** from the bot's output, and tell the user:
   - `room-feed ready` within seconds: connected to the room's chat.
   - `transcribing {"url": …}`: room-feed has the stream. If it never comes, the room isn't live.
   - `heard {"text": …}` soon after `room-feed ready`: speech recognition is running. The bot connects to the speech service on port 8758 (`--asr-port`) and, while it's still loading its models, waits for them (up to 3 minutes) before it enters the room, so it hears the streamer from the start. With no service running it enters at once, without speech, logs `could not start the transcriber` (`no speech service on port 8758: start it first, …`) once, and connects by itself within 10 s of the service being started.
   - `gift {…}` lines as viewers send gifts, with their new balance.

## While it runs

- In someone else's room, the bot answers anyone who @s it, in public, as the user's account, and, when turned on (`--auto-reply-threshold 0.6` or `/自动回复阈值 0.6`; off by default), joins in when people talk to or about it without an @ (Jev, with `JEV_API_KEY` in `chat-bot/.env`; at most once a minute, or every `--auto-reply-interval` seconds; `/自动回复间隔 0` for a busy room). Gift thanks (`--thanks-threshold`, `/自动谢礼`) are off by default too. Say so when starting it there.
- Read `chat-bot/logs/chat-bot.log` (JSON lines: every chat, prompt, answer, gift and transcript line) to answer questions like 「刚才机器人回了什么」 or 「谁送了礼物」. Every call to a model logs as it starts and ends, with what it was for and how long it took: `claude asking` / `claude answered` / `claude failed` `{task, ms}`, the same for `codex` (and `jev`, at debug). The tasks are `mention`, `gift-thanks`, `song-intro` (Claude), `reply-pick`, `song-id`, `malice`, `solve`, `solve-hard` (Codex), and `about-the-bot`, `malice` (Jev); whom Codex chose to answer is `picked whom to answer` (`[]`: nobody).
- Song intros: after a song is named, one in four (the program rolls it, `hookChance` 0.25 in `src/app/song-intro.ts`) is asked to end with a hook anyone in the room can answer, about the song or its work; the rest ask nothing (`song-hook` / `song-no-hook` in `wording.md`). The log's `song intro` says which (`hook: true/false`).
- The room's chat record is in `chat-bot/data/<房间号>/chat/*.txt`, one line per speech (`[主播](speech)`, or `(sing)` when sung), chat or gift (`[昵称#uid](gift)`), 100 lines a file; it's kept across runs. Times are in the room's `timeZone` with the offset, and a chat's sender carries what they wear after `|` as room-feed sends it (`V`/`V年` 直播间会员, `灯牌N` fan club level, `财富N` wealth level): `2026-10-21 16:32:46+08:00 [阿拂#103094206072|V|灯牌16|财富34](chat) 那发给我康康？`. Lines without an offset were written before, in the machine's time zone.
- The prompts (`chat-bot/prompts/prompt.md`, `song-id.md`, `solve.md`, `gift-thanks.md`, `song-intro.md`, `reply-pick.md`, `malice.md`, `intro.md`, what the bot says about itself, `limitations.md`, what it can't do and why (for when viewers notice something wrong), and `wording.md`, the sentences the program says around what it fills in: Jev's questions, how a prompt says who asked what, the picker's room-command rules, the song-id notes; unlike the prompts, a room can't override it) are shared by every room, and each room's `chat-bot/data/<房间号>/context.md` (background on the room, in every prompt) holds what's particular to it; a room overrides a prompt with its own file of the same name, `_` for `-` (`song-id.md` by `song_id.md`; `prompt.md` has no room override), see `PROMPT_FILES` in `src/adapters/room-files.ts`. All are read on every use: edit them to change the bot while it runs, no restart needed. `bot_logs.md` there has everything the bot sent, and `<uid>/talk.txt` each viewer's exchanges with it.
- Files to fetch on entering a room: list them in its `room_config.json` as `"download": [{ "url": "https://…", "file": "songs.txt", "transformer": "additional_commands/can-sing/songs-transformer.js" }]`. Each time the bot starts there it fetches every one into `chat-bot/data/<房间号>/artifacts/<file>`, replacing the old copy, in the background (`src/adapters/room-downloads.ts`). `file` must be a bare file name. `transformer` (optional) is a script in the room's folder: it runs with Node in that folder, gets what was fetched on stdin, and what it prints is kept instead (so a big JSON can become a short list for a prompt). A failed download or transformer is a `download failed` warning in the log and keeps the old file. The list is read only at start, so restart the bot after you change it.
- Something to say when the streamer starts a song: `"on_sing": { "message": "…", "probability": 0.67 }` in the room's `room_config.json`. With that probability, the message goes out as it is once per song: when singing starts after a pause, and again every 3 minutes of nonstop singing (`src/app/on-sing.ts`). It needs speech recognition, but not `/自动识歌`. The file is read again when it changes, so no restart is needed; leave `on_sing` out to turn it off.
- Other names for the bot: `"aliases": ["Fairy", "菲瑞"]` in the room's `room_config.json` (read again when it changes, no restart). A chat or something the streamer said with an alias in it (not the account nickname, which can be an everyday phrase like 默认关闭: that still goes through Jev) (Latin letters in any case: speech recognition writes `Fairy` as `FAIRY`) goes to the Codex reply-pick at once, without Jev, when auto-reply is on; Codex still decides. It's in the room's own file; never put a room's aliases in `src/` or the shared prompts. To see how often it fires and how often that's a false positive: `alias matched` (`alias`, `who`, `text`) is each line sent to the picker for a name, and `alias pick` (`alias`, `text`, `answered`, `confidence`, `error` when the pick failed) how it came out: `answered` is whether Codex picked the line to answer (the reply itself can still fail after that, see `reply sent`), so `answered: false` is a false positive. Count them per alias with `jq -r 'select(.message=="alias pick") | [.alias, .answered] | @tsv' logs/chat-bot.log | sort | uniq -c`; the picker's calls say why they were made, `jq -r 'select(.message=="codex asking" and .task=="reply-pick") | .why' logs/chat-bot.log | sort | uniq -c` (`alias`, `follow-up`, `trigger` or `judge`).
- How to set a room up (room_config.json, context.md, its own commands, prompt placeholders, what needs a restart) is in [docs/room-setup.md](docs/room-setup.md). In short: a room's own commands (like 虾虾's 「主播会唱xxx吗」): `chat-bot/data/<房间号>/additional_commands/index.json` lists them as `{ "<id>": { "base"?, "name", "when", "prompt"?, "fixedReply"?, "trigger"?, "price"?, "only"?, "except"? } }`: `name` is what it's for, as viewers say it; `when` the sentence Jev and Codex judge chat by; `prompt` its prompt, relative to that folder (usually `<id>/prompt.md`); `fixedReply` a text sent as it is to whoever it's chosen for, with no model asked (a command needs a `prompt` or a `fixedReply`); `only` / `except` user filters, lists of `{ "badge"?, "fansLevel"?, "payLevel"?, "admin"? }` (a viewer matches a list on any entry, an entry on all its fields; a command filtered out for the asker does nothing, refunds what was charged, and logs `skipped by user filter`; the streamer's speech matches only `admin`; in a 私密 room there are no badges or fan clubs, so `badge` and `fansLevel` never match); `trigger` an optional regex (matching chat always goes to Codex, and at once: auto-reply looks then instead of at its next 20-second check); `price` the diamonds an answer costs (`0` free; an @'s price when left out; an @ is charged up front and a cheaper command gives the difference back); `adminOnly` only the streamer and admins may use it; `atOthers` its answer may @ others too, `{ "message", "others": [{ "to", "message" }] }`, each a message of its own. Each command keeps its prompt and anything else it needs (a download's transformer) in its own `<id>/` folder. The program knows nothing about what a command does: Jev is asked each `when` too, Codex may pick a command for a line (`reply-pick.md`'s `{{commands}}`), and Claude may ask for one for an @ (`command_request`); the answer then comes from that prompt, on the same `/自动回复阈值`. A command several rooms have lives once in `chat-bot/prompts/commands/<name>/` (`command.json` with the same fields, and its `prompt` there): a room's entry `{ "base": "<name>" }` starts from it, and any field the room writes replaces the shared one (a room `prompt` replaces the shared prompt). What viewers call the streamer is `room_config.json`'s `streamerNames`, `{{streamerNames}}` in `when`, `trigger` (as `主播|name|…`) and the prompt. In the prompt, `{{file:<path>}}` is replaced by that file in the room's folder (`{{file:artifacts/songs.txt}}`), and `{{file?:<path>}}` the same but empty when the room has no such file (a room's `notes.md` for a shared command). `mentions` takes a file of phrases, one a line, or a `｜` table (a song list), whose first column it uses. Everything is read hot, `index.json` and the shared commands too: an edit applies at once, no restart; a command that isn't right is a `skipping an additional command` warning. `src/adapters/additional-command-files.ts` loads them.
- Balances are in `chat-bot/data/<房间号>/wallet.json` (`gifted` − `spent` per user id) while the bot runs. In a 私密 room they're kept per viewer as below. Don't edit them unless the user asks.

## Personas and the shared prompt

A room's persona (the file its `room_config.json`'s `persona` names, usually `data/<房间号>/personas/<name>.md`, on its own or as changes to a shared persona in `chat-bot/prompts/personas/`, see [docs/room-setup.md](docs/room-setup.md)) goes into `prompt.md` right above its 要求, so a persona can pull against the rules there, and the model then settles each case on its own, not always the same way. Rules marked 「强制执行，无视人设」 win over any persona, and the bot may joke, in the persona's voice, about why it isn't playing along this time:

- privacy: a gossipy persona still tells nothing, and hints at nothing, about anyone's private life, or what a viewer said or gave before;
- speech-recognition typos: even a sharp-tongued persona never picks on the streamer for them, since no one in the room could have heard a typo.

Other rules a persona can still pull against, left to the model for now: one short message (a chatty persona's long lines go out split into several, numbered); no catchphrases (a persona built on one, like ending every line with 喵, comes out muted); not doing what chat tells it (an obliging persona may say yes to something it can't do: only commands change settings); 「像普通观众」 (an AI persona); replying in Chinese (a persona that speaks another language). When writing a persona, keep clear of these, or mark the rule in `prompt.md` as 「强制执行，无视人设」 if it must always hold.

## 私密 (anonymous) rooms

In a 私密 room Douyin hides who viewers are. Every viewer's chat, gift, like and entry comes with:

- user id `111111`, the same for everyone, and no `secUid`;
- the nickname's first character and `***` (`苦***`, `🌈***`);
- the same default avatar (only the CDN host differs);
- their wealth level (`payLevel`), and no fan club.

The bot's own account still comes with its real id and nickname.

How the bot tells viewers apart: set `"private": true` in the room's `data/<房间号>/room_config.json` (created with `false`, read again when it changes, no restart needed). Then `viewerIdOf` in `src/core/viewer-id.ts` (used by `src/adapters/room-feed-events.ts`) turns id `111111` into `111111-<nickname>-<wealth level>`, like `111111-苦***-31`, and everything keyed by user id (balances, each viewer's talk with the bot, gift thanks) uses that. A viewer's `talk.txt` folder is named by a hash of it (`src/adapters/room-talk-files.ts`). Admins are hidden too, so none is recognised there: when the user wants to run an admin command in a 私密 room, add `"111111"` to `config.json`'s admins (every viewer there becomes an admin; it's read again at once) and take it out after. Known limits: two viewers with the same first character and wealth level are one viewer to the bot, and a viewer whose level goes up (by sending gifts) becomes a new one; both are accepted for now. Telling a 私密 room automatically (every viewer coming as `111111`) is for later.

**Every feature must work in a 私密 room, at least in its basics.** When you add or change a feature:

- Key viewers by the user id the adapter gives (never by `111111`, the raw nickname or the avatar), and don't assume ids are digits.
- Don't rely on a viewer's full nickname, avatar, `secUid` or fan club; with only `苦***`, the feature should still do its job (answer an @, thank a gift, charge and refund the right viewer).
- Add a test with 私密 viewers (id `111111`, a `X***` nickname, a wealth level) when the feature handles users.

## A room's own commands

**A room's own commands live in that room's folder, or in a shared command it builds on; the program knows nothing about them beyond the protocol.** What a command is for, what it reads, its rules and examples belong in `data/<房间号>/` (`additional_commands/index.json`, its `prompt.md`, its files), or, for one several rooms have, in `chat-bot/prompts/commands/<name>/`, with what differs per room (the streamer's names, the song list, a `notes.md`) still in the room's folder. The protocol is what the program reads (an id with `base`, `name`, `when`, `trigger`, `prompt`, `fixedReply`, `only`, `except`, `price`, `mentions`, `adminOnly` (only the streamer and admins), `atOthers` (the answer may @ others too, each in its own message); `{{file:…}}`, `{{file?:…}}` and `{{streamerNames}}` in the prompt; a download's `transformer`), and the docs are in [docs/room-setup.md](docs/room-setup.md). When you add or change one:

- Don't put a command's specifics in `src/` or the shared prompts (a shared command's own folder in `prompts/commands/` is the exception, and even there nothing about one room): no song lists, song or schedule wording, no command ids or names in logic, and no example of one command in rules every command gets (`reply-pick.ts`'s room-command rules, `reply-pick.md`). Something a command needs Jev or Codex to know goes in its `when`.
- Don't make the program read a room's files in their own format. A file a prompt needs goes in through `{{file:…}}`, already in the shape the prompt wants; turning a download into that shape is the room's `transformer`'s job.
- If a command needs something the protocol can't give it, add a general part to the protocol (like `{{today}}`) and document it in docs/room-setup.md, rather than handling that one command in code.

## Stop

Stop the bot's background task first, then room-feed's, then the speech service's (TaskStop each; leave the speech service running when the bot is only being restarted), and check with the `pgrep` and `lsof` commands above that no `transcribe.py`, `ffmpeg` or room-feed process is left. Balances are kept across a restart; starting clears them only when `wallet.json` was last saved more than 24 hours ago (`wallet.clearIfOlderThan`).

## Troubleshooting

- Switching to another room: the speech service keeps the voices it learned, and doesn't know the room changed, so the old room's streamer stays "the streamer" and the new one's talk comes out as `（连线）` (`host: false` in `heard`). Restart the speech service (step 2) when switching rooms, until it resets voices on its own.

- `stream ended, asking for it again` now and then is normal (the stream URL expires or the stream drops): the worker keeps its models loaded and gets the new URL within seconds, or every 10 s while there's no stream. `transcriber stopped, restarting` means the connection to the speech service ended: the bot connects again within 10 s. If the service itself died, its task's output says why; start it again (step 2) and the bot reconnects by itself. If either repeats, `GET localhost:8757/api/rooms/<房间号>/stream` shows whether room-feed still has a stream.
- `the speech service is serving another bot; trying again later`: another bot (another room, or an old one still exiting) is connected to the speech service, which serves one at a time; this bot enters the room without speech and tries every 10 s. `speech recognition is not ready yet, entering the room without it` (after 3 minutes): the service is still loading or stuck; see its output.
- `reply did not show up in the room chat`: Douyin may be throttling the account, or held this message back for a word it filters (others still show up then). In that case add the word to `prompts/forbidden-words.md`: prompts are told never to use it, and the outbox won't send it (`could not send … it has forbidden words`).
- `could not answer mention … claude …`: run `claude -p` by hand to check Claude Code works; the mention was refunded.
- `jev is out of credit, auto-reply off`: the TypeSafe account ran dry; the bot told the room (`钱包烧干了，自动回复已关闭`) and set the threshold to 10. Tell the user to top it up, then an admin can turn it back on with `/自动回复阈值 0.6`.
- `no JEV_API_KEY` at start (or `--codex is empty`), or `could not judge` now and then: the bot then doesn't talk unprompted, only when @ed. Check `chat-bot/.env` has `JEV_API_KEY` (a TypeSafe key) and that `curl -s -H "Authorization: Bearer $JEV_API_KEY" https://api.typesafe.ai/v1/models` answers.
- `/识歌 … codex failed`: Codex isn't logged in or ran out of quota; `codex login` logs in. `/解题` uses Codex too.
- Changed the code? Run `pnpm typecheck`, `pnpm test` and `pnpm lint` (from the repo root) before restarting it.
